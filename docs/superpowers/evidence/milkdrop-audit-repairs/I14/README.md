Original MilkDrop2 source remains the oracle for its stated CPU operations, not a Windows pixel oracle. Preserve Native rendering, trails/detail/diffusion, line scaling/antialiasing, minimum lengths, positive GPU warp powers, CPU rotation/negative-power transport, prepared replay and per-preset ownership.

## Four boundaries that must not be merged

1. **Original node producer and CPU reverse propagation.** `milkdropfs.cpp:1514–1548` indexes raw rows from fy, interpolates four float UV corners in A/B/C/D accumulation order, then returns `(tu,1-tv)`. Original nodes were computed after equations, with CPU powf/trig, original row orientation and half-texel offsets. Interpolation has no dependence on feedback triangle topology, raster pixels or float16 storage.
2. **Current warp node producer.** Current PerPixelMesh prepares evaluated attributes once, then vertex shaders compute final UVs. Positive powers/oscillators remain GPU arithmetic; rotation and negative zoom have specific existing CPU policies. The repaired legacy Y oscillator and AD diagonal do not convert current motion reconstruction into original bilinear semantics.
3. **Current triangle/raster/filter reconstruction.** Motion shaders sample the previous full-canvas UV texture at `(x,1-y)` in both GL-line and Native quad paths. Fragment interpolation is piecewise affine over triangles; linear texture sampling reconstructs that rasterized map, not the four raw node UVs. V flipping and raw row selection must be proven independently. Merely switching the diagonal or sampling a bilinear version of the physical warp image is insufficient.
4. **RG16F conversion and shader precision.** MilkdropPreset allocates GL_RG16F. Conversion is an additional boundary; current warp VS/fragment and GL-line VS default mediump, while Native quad VS is highp. Removing float16 storage does not itself remove limited shader arithmetic. `.173` float32→half has a small nonzero error, but the handoff's RTZ result is not a universal GLES rule.

There is another explicit producer limit: current ProjectM defaults texel offsets to0 and WarpedBlit divides those configured offsets by render-context viewport dimensions; original CPU nodes include .5/texture-size. No new half-texel restoration is included in I14. Stage-injected final corners isolate interpolation from that producer difference. Declare configured offsets, render-context viewport and actual UV allocation separately when testing real presets.

## Minimal alternatives and cost

**A — CPU source-derived node UVs and CPU bilinear endpoints.** Consume already prepared/evaluated attributes; do not execute EEL a second time. Compute a per-preset prior node map, mirror original raw-row semantics explicitly, and interpolate endpoints before uploading them to existing vector geometry. This needs no readback/full-size new target. It introduces a distinct motion producer, including CPU positive powf and up to four oscillators per node; feedback must keep its current GPU producer. Original source parity of that arithmetic requires separate bounded precision qualification. Computing only for the active-vector gating preserves I16's separate stale-map policy.

Counts: N=(Gx+1)(Gy+1), M≤64×48=3072 vector starts. Up to2N pow evaluations,4N oscillator trig evaluations and four once-per-frame warp-factor cos evaluations; existing CPU rotation components can be reused. Up to M four-corner interpolations. Four float weights need2 subtractions/4 multiplications; each vec2 weighted sum adds8 multiplications/6 additions plus final1−V. One float32 vec2 map needs8N bytes; two retained generations16N. Endpoint pairs require16M bytes if both start/end are stored, or8M bytes for ends alongside existing starts. No timing claim follows.

**B — compact GPU node capture, explicit four-fetch bilinear reconstruction.** Reuse prepared attributes with a dedicated legacy UV vertex program and N-point transform-feedback draw under rasterizer discard. Transfer the resulting float32 vec2 buffer to a(Gx+1)×(Gy+1) RG32F texture through a pixel-unpack buffer, then use four explicit texelFetch calls and source-order weights. RG32F need not be color-renderable or linearly filterable because it is uploaded and explicitly fetched. These basic buffer/texture operations are specified by [GLES3.0.6 §2.15, §3.7.1 and table3.2](https://registry.khronos.org/OpenGL/specs/es/3.0/es_spec_3.0.pdf); actual program/cache/driver behavior remains untested. Core GLES3 has no assumed samplerBuffer route here.

This avoids CPU transcendental duplication and full-size raster/half boundaries, but still repeats N GPU vertex computations and preserves GPU-versus-original-CPU differences. It requires new shader/link/cache/TF ownership, RG32F texture/PBO state, row/V semantics and generation/resize/context-loss handling. A single TF buffer and texture need16N bytes; ping-pong textures plus TF buffer need24N. Normalized-field updates write8N to TF and upload8N to texture. Native quads invoke reconstruction four times/vector, up to16M explicit fetches (49,152 at max M); GL-line odd endpoints need4M (12,288). Preserve both paths' existing line/minimum styles and qualify any narrowly introduced highp arithmetic separately.

**C — full-size RG32F replacement only.** Removes half storage only, leaves triangle/raster/filter errors. Adds4WH bytes persistent memory and logical write payload per refreshed frame. At actual1280×720:3.515625MiB; at actual3840×2160:31.640625MiB. This is a poor standalone I14 repair and cannot be called original reverse propagation.

**Recommendation:** first prove the revised injected-corner and row/V controls. Prototype B if its API/state cost is acceptable and declare it a compact GPU motion-field policy. A is a source-oriented fallback but has material CPU cost and arithmetic policy implications. If neither passes focused Native4K cost/lifecycle gates, defer I14 with explicit triangle/raster/RG16F semantics. No candidate implementation is approved by this source-only preparation.
