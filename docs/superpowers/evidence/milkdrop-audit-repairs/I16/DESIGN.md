# I16 disabled-motion UV: source-only proposal

## Correction: no GetUV API

No GetUV symbol was found in inspected production engine/API, core tests or analyzer native adapters. The actual production query is `texture(warp_coordinates,vec2(pos.x,1-pos.y)).xy` in PresetMotionVectorsVertexShaderGlsl330.vert; Native quad motion uses its equivalent GPU texture query. Do not invent a public Android/C query API. MotionVectors::Draw consumes a stale texture on re-enable, so stock visible rendering can expose the issue.

## Proposed bounded lazy repair / owner decision

Preserve disabled-frame write optimization. Existing prepared GPU mesh arrays/index buffer remain previous frame's equation outputs until next InitializeMesh/CalculateMesh, which follows motion drawing. Retain compact metadata AFTER actual prior warp vertex uniforms are bound: frame/context/target/canvas dimensions, compiled default/custom/failed-fallback path, topology generation, warpTime/warpScaleInverse/warpFactors, aspect/inverse aspect and normalized texel offsets. Snapshot actual publication-target producer, not future live state. Do not copy noncopyable PresetState/PerFrameContext or retain retired textures/handles.

At non-first active frame, if published map generation is older than compatible retained completed warp, draw existing previous mesh once into existing RG16F attachment via dedicated UV-only framebuffer/program and frozen previous vertex uniforms. Restore draw/read FBOs, draw buffers and viewport on exit; mark generation only on success. Perform once BEFORE either native or canvas motion consumer. Then current frame proceeds normally; do not reexecute any equations or initialize/recalculate the retained mesh.

Existing DrawAgain is UNSAFE across frames: WarpedBlit rebuilds time/aspect/texel uniforms from current state, binds custom fragment uniforms/samplers and invalidates COLOR_ATTACHMENT0/1. It is a current-frame replay facility. A narrow UV-only method must avoid color0 output/invalidation and live fragment execution.

Custom shader translation MilkdropShader.cpp:491 initializes `_mv_tex_coords.xy=_uv.xy` before shader_body; ordinary later uv mutation does not change its published map. A dedicated fragment can output previous vertex-produced UV for bounded non-discard programs. `clip`/discard preserves old UV at discarded pixels; generic UV-only coverage would silently change that behavior. Do not weaken discard semantics. Hidden direct writes to injected `_mv_tex_coords` also invalidate generic reconstruction. Universal lazy coverage needs a stronger producer contract or an explicit separate fallback. Continuously publishing real UV for those programs forfeits disabled-frame bandwidth optimization and is an owner tradeoff, not accepted here.

## Cost/storage and disposition

One extra UV-only mesh pass plus FBO/viewport switch per stale re-enable, not every disabled frame. Mesh48x32 means1617 vertices/9216 indices/3072 triangles. RG16F nominal output4 bytes per pixel:147456 bytes at256x144 or33177600 at native3840x2160. These are output payload arithmetic, not measured bandwidth/time. Small per-preset previous-uniform/generation storage and CPU bookkeeping also cost. Frequent toggling can add a pass every re-enable; discard-preserving continuous-write fallback adds bandwidth each disabled frame. Owner deferral is appropriate if those costs/new ownership are unacceptable. No apply-ready universal patch or acceptance claim before producer/ownership validation.
